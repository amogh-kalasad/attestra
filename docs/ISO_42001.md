# ISO/IEC 42001:2023 readiness pack

Attestra ships a framework pack for **ISO/IEC 42001:2023**, the management-system standard for AI (the AIMS). Its framework key is `iso_42001_2023`.

## What this is and what it is not

- This is a **readiness / reference check**. It is **not a certification** and Attestra output must never be presented as one.
- Certification bodies that audit and certify against ISO/IEC 42001 work to **ISO/IEC 42006:2025** (published 2025-07-07), on top of ISO/IEC 17021-1. Only an accredited body can issue a certificate.
- All titles, checks and verification steps in the pack are **our own words**. The standard is copyrighted. Check every reference against a licensed copy of ISO/IEC 42001 before relying on it in an audit.
- The control list was cross-checked against the official contents preview and independent public lists (see `reports/ISO42001_VERIFIED_CONTROLS.md`). The OWASP and CWE mappings are our engineering judgement; no official ISO-to-OWASP mapping exists.

## How the roll-up works

1. Every 42001 ref is fed by an `assessor_evidence` objective, so it starts as **not_assessed**.
2. Tool objectives add findings by CWE. Because the weakest status wins, findings can push a control down to `partial` or `not_met`, but a clean scan can **never** make a 42001 control `met` on its own.
3. An assessor confirms each control (met / partial / not_met / not_applicable, with a rationale). A confirmed status always wins.

Website checks on the AI endpoint (TLS, headers, authentication) are mainly ISO 27001 evidence. Under 42001 they only *support* A.6.2.5 and A.6.2.6.

## Check types and verification

| Check type | Meaning | How it is verified |
| --- | --- | --- |
| `tool` | A scan or test gives evidence. Always partial support. | Imported results plus a retest after each fix. Request/response proof via the proof and replay feature. |
| `evidence` | A document or record is reviewed. | Document with version, owner, approval and date. |
| `assessor` | Needs interview, judgement or sampling over the period. | Assessor notes; running controls are sampled with the seeded sampling used for SOC 2 and ISO 27001 clause 9.2. |

Controls with a meaningful tool part: A.4.4, A.4.5, A.6.2.4, A.6.2.5, A.6.2.6, A.6.2.8, A.9.2, A.9.4, A.10.3 (optional light checks: A.3.3, A.7.4, A.7.5, A.8.2, A.8.3). Everything else, and all of clauses 4-10, is evidence or assessor only.

## Prompt-injection and LLM probe tests are active testing

Prompt injection, jailbreak, leakage, excessive-agency and resource-abuse probes (every `llm_top10` entry with `active_test: true`) send crafted input to a live system. They are **active testing**:

- They need **written permission** from the system owner, recorded as a valid signed authorization on the engagement, and proof of ownership for the target.
- The asset must have **`intrusive_allowed`** set. Without both, do not run or import probe results.
- Passive checks (TLS, headers, exposed files) do not need `intrusive_allowed`, but still need the signed authorization.

An LLM probe importer (for example garak or promptfoo output) is planned but not built yet; until then, record probe results as findings with the CWEs above.

## Statement of Applicability (clause 6.1.3)

- **Works now:** the `iso_soa` report kind takes a framework, so `generate_report(..., kind="iso_soa", framework="iso_42001_2023")` renders a 42001 SoA view from the roll-up. The 42001 evidence pack zip also contains `iso42001/statement_of_applicability_draft.csv` for the 38 Annex A controls.
- **Needs a schema change (not done):** the stored, editable SoA (`soa_entries`, `services.generate_soa`) is keyed by `(engagement_id, control_ref)` with no framework column, and `generate_soa` is fixed to ISO 27001. 42001 refs such as A.8.3, A.8.5 and Clause 6.1.2 clash with ISO 27001 refs. To make the 42001 SoA editable:
  1. add a `framework` column to `SoaEntry` (default `iso_27001_2022`) with a migration, and change the unique constraint to `(engagement_id, framework, control_ref)`;
  2. give `generate_soa`, `list_soa` and `update_soa_entry` a `framework` argument (default ISO 27001);
  3. let the ISO page and API pick the framework, and make the exclusion message name 42001 clause 6.1.3 for that framework.

## Running an assessment

1. Create an engagement with `iso_42001_2023` in its frameworks (often next to `iso_27001_2022`).
2. Record the signed authorization; set `intrusive_allowed` only on assets where active AI testing is approved.
3. Import scan results and any approved LLM probe results.
4. Review the compliance view for `iso_42001_2023`: every control starts as not_assessed.
5. Collect the evidence listed in each `verify` step, interview and sample, then confirm each control with a rationale.
6. Build the evidence pack (`iso42001/check_register.csv` lists check types, verification steps, LLM ids and CWEs per control).
